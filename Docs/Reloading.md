# 生命周期、加载顺序、Harmony 与重启

本文说明《舒舒服服小岛时光》配套 Mono Player 的 Mod 生命周期。玩家按界面提示管理作品；作者通过清理、稳定身份和明确的内容准备阶段，使作品可以可靠启停。接口细节见 [API.md](API.md)。

## 应用时机

| 操作或状态 | 行为 |
| --- | --- |
| 菜单中启停可清理作品、修改其配置或调整顺序 | 重建运行上下文，下次进入世界使用新组合 |
| 首次开启尚未加载过的 DLL，未声明需要重启 | 可在菜单加载，不因含 DLL 就强制重启 |
| 停用、重新开启同一份 DLL，清理完整 | 可切换；程序集仍驻留，行为与对象重新建立 |
| 已加载 DLL 字节变化，包括停用后替换 | 保留当前可用组合，保存选择并提示完整退出重启 |
| `requiresRestart: true` | 进程初始配置按保存选择加载，之后相关组合变更延后到下次进程 |
| 卸载、登记清理或补丁撤销失败 | 提示重启，停止构造混合状态 |
| 世界运行中托管回调失败 | 暂停失败作品的回调与补丁，保留现有实例所需模板/归属/资源，到菜单再清理 |

列表勾选表示已保存选择。显示待重启时，进程内当前组合仍保留；进入世界或回到标题不等于重启进程。扫描和 Steam 下载事件不会在世界中热换类型集合。

只有无法完整撤销效果的作品才声明 `requiresRestart: true`，例如无法停止的后台工作或不可逆原生状态。设置为 `false` 不能强行卸载旧程序集或绕过 DLL 哈希检查。

## 加载顺序与依赖

拖动序号手柄时，卡片限制在列表中上下移动并预览顺序；松开才保存。Esc 或拖出列表松开取消。鼠标靠近上下边缘会持续自动滚动；普通浏览可用滚轮。

顺序按账号保存，新作品追加。必要依赖先于使用者加载，拖动不能破坏这条约束；缺失、版本过低或循环依赖报错。依赖字段结构见 [Manifest.md](Manifest.md)。仅调整顺序也可能重建上下文，因此 `OnLoad` 不能假定进程中只执行一次。

通常反序卸载，使使用者先于依赖清理。Harmony 的优先级和补丁规则仍会影响执行次序；两个 Mod 修改同一原生方法时，排序不能消除所有语义冲突。注册物品的稳定身份来自 Mod UUID 与局部 ID，不随列表位置变化。

## 上下文与清理

把自建组件和临时对象放在 `context.Root` 下，用 `OnUpdate`、`OnSceneLoaded` 登记托管回调。额外事件订阅、原值替换、全局缓存、材质、线程和外部资源使用 `AddCleanup` 或自己的明确退出路径管理。

正常结束先调用 `OnUnload`，再释放上下文、逆序执行清理，撤销本 owner 补丁并释放托管注册。不要在 `OnUnload` 中全局清理别人的资源。清理应容许原生场景对象已经销毁，并避免再次调用时破坏其他作品。

`OnLoad` 若只执行一部分就抛异常，加载器会释放该上下文并执行已登记的清理，`OnUnload` 不会被调用。每取得一个需要释放的资源，就立即登记对应清理，不要把所有 `AddCleanup` 留到 `OnLoad` 最后。例如 `AssetBundle.LoadFromFile` 成功后，先登记该 bundle 的释放，再读取其中的 Prefab 或安装其他行为；否则后续资源缺失时，加载失败虽能阻止入世界，尚未登记的 bundle 仍会泄漏。作者静态入口、原生事件和自有材质遵循相同规则，清理只作用于当前实例持有的对象。

`OnContentReady` 的同步准备与普通场景/逐帧行为不同：它在读档和网络生成需要模板之前执行，要求幂等；运行世界冻结类型集合。使用 `FindPrefab` 防止重复登记，按当前场景重新发现管理器。不能把异步生成、等待玩家出现或后续首帧注册当作准备已完成。

世界中发生故障时，暂停和最终释放也是两个阶段。底座暂停托管 Root、场景回调和 Harmony，暂时保留模板与资源，避免已有实例失去定义；回菜单后再处理释放。作者自行订阅的外部事件或后台任务仍需自己的错误与停止逻辑。暂停的上下文尚未释放，原生事件入口还应检查托管 `Root` 是否活跃。此时的世界状态保存沿用[上次成功读入或提交的记录](Save-Data.md#登记与回调)。

停用行为清理与存档迁移相互独立。已登记物品定义缺失时，读档按保存归属目录备份并清理已知引用；重装不会补回已经另存删除的物品。世界任务状态应使用 [RegisterSaveData](Save-Data.md) 同版本保存和迁移；地图结构与作者网络协议不自动获得兼容保护。

## 为什么 DLL 更新必须重启

`Assembly.Load` 加载代码，不会让旧类型、静态状态、事件、Unity 组件或 Harmony 补丁自动失效。当前 Unity Mono 主域不能单独卸载一个任意程序集。重新读取相同文件不等于卸载旧版本；加载器通过程序集身份与内容哈希识别更新。

停用负责清理行为和资源，程序集保留到进程退出。Unity Editor 的 Play Domain Reload 不是 Player 主菜单可调用的热重载能力。当前底座没有脚本虚拟机或可收集执行域；不要反复换程序集名规避重启检查。可调整的参数可以放在作者自己的 JSON 中，通过正常生命周期重新解析。

## 游戏提供的 Harmony

所有作品共享游戏固定提供的 HarmonyX 运行时，通过 `context.Harmony` 得到按 Mod UUID 隔离的 owner：`cozy.mod.<uuid>`。玩家不需要额外订阅 Harmony 前置作品，作者也不要把另一份 `0Harmony.dll`、MonoMod 或 Cecil 带入包。

加入 macOS Universal 模组支持后，Windows x64 和 macOS Universal 的 Mono 游戏构建共用同一套依赖。下表列出这次升级锁定的程序集版本。

| 程序集 | 游戏运行时版本 |
| --- | --- |
| `0Harmony.dll`（HarmonyX） | 2.16.0.0 |
| `MonoMod.RuntimeDetour.dll` | 25.3.3.0 |
| `MonoMod.Utils.dll` | 25.0.11.0 |
| `Mono.Cecil.dll` | 0.11.6.0 |

编译时使用配套游戏安装目录里的程序集。依赖版本随游戏构建而定，更新游戏后用新版程序集重新编译。游戏在运行时加载 `MonoMod.Backports.dll`，范例项目会将它从编译引用中排除，以避免与 Unity Mono 自带类型重复。 [编译方式](../Tools/README.md#直接编译)

使用 `context.Harmony.Patch(...)` 或仅对自己的补丁类型/程序集 `PatchAll(...)`。正常上下文清理只撤销该 owner；作者不得调用全局 `UnpatchAll()`。需要主动撤销自己的补丁时使用 `UnpatchSelf()`，并负责恢复额外静态状态和缓存。撤销补丁不会自动复原之前已改写的字段值。

[MinimalCodeMod](../Examples/MinimalCodeMod/README.md) 修补自己 DLL 的 NoInlining 方法，能验证加载、补丁及重新启用时的撤销结果。[BuildingHints](../Examples/BuildingHints/README.md) 修补原生建筑 getter，需要随游戏版本测试。使用 Harmony 与直接调用原生 API 都必须核对实际语义，owner 隔离只管理归属，不自动解决玩法冲突。
