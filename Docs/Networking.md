# 作者网络消息与缺包边界

本文面向使用配套 Mono Player 的 C# Mod 作者。基础层处理已登记 Prefab 的网络身份与缺包容错；`RegisterSaveData` 负责房主世界存档，**不会自动同步任务进度、作者 HUD 或任意字段**。存档契约见 [Save-Data.md](Save-Data.md)，已登记内容的范围见 [API.md](API.md#保存联网与失败时的生命周期)。

## 进入世界前的模组准备

游戏检查发起操作的本机启用项。Steam 加入请求遇到模组扫描、订阅下载等仍能完成的准备工作时，会在主菜单静默等待，准备就绪后才开始连接。如果等待时又发出加入请求，只有最新请求会继续。退出主菜单会中止等待。遇到清单错误、准备失败或需要重启时，先按反馈处理。新建世界、读档和局域网加入在入口直接检查，准备完成后重新操作。

客机仅因缺少房主的已登记物件定义时，仍可进入并跳过相关对象。若客机自己已启用的作品报错，则要先处理本机问题。被跳过的物件和背包显示不会清理房主的存档；任意作者协议仍需自行兼容。

## 一个不依赖额外 Bridge 的已测路径

[ResearchCamp](../Examples/ResearchCamp/README.md) 的作者实现位于 [CampMod.cs](../Examples/ResearchCamp/Source/CampMod.cs)：

1. 房主才推进任务、改变物品或发奖励；客机仅展示房主快照。客机收到状态不调用世界保存接口。
2. 作者定义独立命名空间中的 `CampHello` 与 `CampSnapshot` 消息，并显式设置 `Writer<T>.write`、`Reader<T>.read`。动态加载的普通作者 DLL 不会自动经过游戏构建时的 Mirror Weaver；仅声明 `NetworkMessage` 并不能据此假定序列化函数已生成。
3. 服务端与客户端在各自网络启动后注册处理器。客机每两秒请求一次；房主检查协议号、状态已恢复，再回复该连接。状态恢复可能早于网络启动，不要因为恢复回调中 `IsHost` 尚为 false 就跳过恢复。
4. 房主不会向所有连接广播作者消息，只回复主动请求的同包客机。因此没有安装该 Mod 的客机不会收到它不认识的作者快照。
5. 退出与清理撤销作者自己的处理器、事件和状态。准备再次进入世界时，重新检查网络生命周期与当前管理器，不能把上一会话的布尔标记当作仍已登记的证据。

这个范例采用普通消息，**没有自定义 `NetworkBehaviour`、SyncVar 或 RPC**。这些能力需要匹配 Player 的 Mirror 编织流程以及单独运行验收；普通消息成功不证明未经编织的自定义网络组件可以直接加载。

## 作者仍要负责的规则

- 世界变更在房主验证；客机的请求不能作为“已满足材料、任务条件或领取资格”的证据。不要让客机直接提交一份 JSON 覆盖房主任务状态。
- 消息命名、协议版本、输入大小、请求频率和内容校验由作者设计。使用自己的类型与处理器，不能覆盖其他作品的协议或全局清空处理器。
- 接收方需要已经准备好相应处理器和序列化函数。范例覆盖“房主有 Mod、客机同包或缺包”，没有验证客机独有 Mod、版本不匹配、恶意请求或高并发。要支持这些组合，应增加明确协商与拒绝行为，再实测，不能从当前 Hello 请求推断任意服务器都能接收它。
- 新加入或重连的客机应重新取得当前世界状态；切世界后不能继续展示上一个世界的快照。用户偏好与房主世界状态分开保存。
- 不在包里放另一份 Mirror 或游戏 DLL。编译引用来自实际 Player；原生网络 API 可能随游戏更新变化。

## 如何判断验证是否足够

ResearchCamp 0.1.0 在同一台电脑两个独立进程中使用 KCP 回环，验证同包晚加入收到物体和任务 JSON、换成缺包客机后继续显示原生玩家、房主状态不变并能保存。它也做过单进程 Steam Host，但没有完成远程 Steam 双账号验证；0.1.1 的定向修订与复验范围见范例 README。

正式多人验收仍应包含不同电脑、不同 Steam 账号、同包、缺包、晚加入、重连和实际客机操作。已通过本机回环不能证明 Steam/P2P、防火墙或远程权限行为。把作品协议的错误、原生场景诊断和测试工具未完成前置条件分别记录，不能仅凭日志出现异常就归因于缺包。
